# 年表データ拡充ガイド

## 目的

同梱年表データを増やすときの進め方、イベント選定、出典確認、検証手順をまとめる。データ形式そのものは[`data-schema.md`](data-schema.md)を正とし、この文書では作業時の判断基準を扱う。

## 基本方針

- まず既存レコードのイベント密度を揃える。
- 1レコードあたり3から5イベントを目安にする。
- 新しい人物や組織を増やす前に、既存サンプルで表示される範囲の薄いレコードを補強する。
- 1回の作業は1テーマ、または近い時代の5から10レコード程度に絞る。
- 事実確認できないイベントは追加しない。

データ量を増やすだけだと年表が読みにくくなる。人物、組織、運動の関係が見えるように、同じ時期の代表作、結成、転機、受賞、解散、制度化などをバランスよく選ぶ。

## 作業単位

推奨する1バッチの流れは次の通り。

1. 対象テーマを選ぶ。
2. イベント数が少ないレコードを洗い出す。
3. 追加候補を3から5件ずつ決める。
4. 各イベントに出典を付ける。
5. JSONを更新する。
6. 検証コマンドを通す。
7. 1目的のコミットにまとめる。

イベント数の偏りは次のコマンドで確認できる。

```sh
jq -r '.histories[] | .id + "\t" + .title + "\t" + ((.events|length)|tostring)' src/data/<topic>.json
```

イベントが少ないレコードだけを見る場合は次を使う。

```sh
jq -r '.histories[] | select((.events|length) < 4) | .id + "\t" + .title + "\t" + ((.events|length)|tostring)' src/data/<topic>.json
```

## イベント選定基準

人物レコードでは次を優先する。

- 生涯やキャリアの転機
- 代表作の発表、初演、録音、出版
- 重要な団体への参加や独立
- 表現様式の変化が見える出来事
- 大きな受賞、評価、死去

組織レコードでは次を優先する。

- 結成、設立、活動開始
- 主要メンバー加入や編成の変化
- 代表作の発表
- 商業的、批評的な転機
- 解散、活動終了、殿堂入りなどの評価

運動レコードでは次を優先する。

- 先行する文化や技法の成立
- 様式を象徴する作品や録音
- 地域、制度、メディアによる拡大
- 次の運動へ接続する出来事

同じレコード内で似た性質のイベントばかり並べない。例えばアルバム発表だけで埋めず、結成、代表作、転換点、評価を混ぜる。

## 日付の扱い

- 年だけ確実なら`{ "year": 1965 }`にする。
- 月日が確認できる場合だけ`month`や`day`を入れる。
- 不明な月日を推測で補完しない。
- イベント日は親レコードの`period.start`以降、`period.end`以前にする。
- 継続中の人物や組織は`period.end: null`を使う。

年表の比較処理では、日付精度の低いデータも扱える。無理に月日を埋めるより、確認できた精度で止める方がデータ品質は高い。

## 出典方針

出典はレコード単位とイベント単位の両方に置く。イベントに対しては、その出来事を直接確認できる出典を優先する。

優先度の高い出典は次の通り。

- 公式サイト、公式ディスコグラフィ、公式アーカイブ
- 美術館、図書館、大学、財団、公共機関
- Britannica、Oxford、Smithsonian、Library of Congressなどの参照資料
- GRAMMY、Pulitzer、Rock & Roll Hall of Fameなどの受賞・評価機関
- レーベル公式、作品公式ページ

避けたい出典は次の通り。

- 出典のない個人ブログ
- 販売ページだけで事実確認が弱いページ
- 同じ内容を転載しているだけの二次サイト
- URLが短期で消えそうなニュース断片

やむを得ず二次資料を使う場合は、できれば別系統の出典も併記する。

## 画像の扱い

画像を追加する場合は、画像URLだけでなくライセンス条件も確認する。Wikipediaの記事で表示されている画像でも、実際の再利用条件はWikimedia Commonsなどのファイル説明ページに書かれていることが多い。

Creative Commonsライセンスの画像では、原則として次を記録する。

- `sourceUrl`: ファイル説明ページ
- `creator`: 作者、撮影者、著作権者
- `license`: ライセンス名
- `licenseUrl`: ライセンス本文または説明ページ
- `modified`: アプリ側で改変したか

Public domain画像でも、来歴確認のために`sourceUrl`、`creator`、`license`を記録する。Fair use、非フリー利用、権利状態が不明な画像は同梱データに追加しない。

## 記述スタイル

- `title`は短く、年表上で読める粒度にする。
- `description`は1文から2文で、なぜそのイベントが重要かを書く。
- 日本語表示を基本にしつつ、作品名、人名、団体名は公式表記や既存データの表記に合わせる。
- イベントIDは親レコード内で一意にし、kebab-caseにする。
- レコードIDを変えない。サンプルの`recordIds`から参照されているため。

良い説明は、事実の言い換えだけで終わらない。

```json
{
  "id": "example-album",
  "date": { "year": 1970 },
  "title": "代表作を発表",
  "description": "新しい録音手法とジャンル横断的な編成を示し、後続の表現に大きな影響を与えた。",
  "sources": [
    { "title": "Official Discography", "url": "https://example.com/discography" }
  ]
}
```

## 検証

JSONを編集したら、まず構文を確認する。

```sh
jq empty src/data/<topic>.json
```

データ検証テストを通す。

```sh
npm test -- src/domain/timelineDataValidation.test.ts
```

コミット前は標準チェックを通す。

```sh
npm run lint
npm run typecheck
npm test
```

表示に影響する大きな追加では、`npm run dev`で年表を確認する。特に次を見る。

- イベントなしのレコードが残っていないか
- 継続中レコードが現在年まで伸びるか
- 人物、組織、運動が混在しても読みやすいか
- 日本語タイトルがツールチップや詳細表示で崩れないか
- 近い年のイベント点が密集しすぎていないか

## コミット

データ拡充は、テーマや時代ごとに小さく切る。

件名例:

```text
ジャズ後半のイベントデータを拡充
ロック年表の代表作イベントを追加
クラシック近現代の作曲家イベントを補強
```

本文には、追加対象、出典方針、確認コマンドを書くとレビューしやすい。

## 次の拡充候補

既存データの密度を揃えた後は、新レコード追加に進む。

- クラシック: 民族楽派、印象主義以後、女性作曲家、現代音楽
- ジャズ: ラテンジャズ、ヴォーカル、ECM周辺、日本ジャズ
- ロック: プログレ、ソウル／ファンクとの接点、ニューウェイヴ以後、インディー、ポストロック

新レコードを追加したら、関連する`samples[].recordIds`も見直す。
